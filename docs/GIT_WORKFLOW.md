# Git・GitHub運用ルール

## 1. コピー先での実装開始時

このスターターで要件確認とプロジェクト生成を行っている間は、生成物のリモート接続を開始しない。人が生成ディレクトリを別の場所へコピーし、そのコピー先で実装起動語を入力したとき、次を行う。

1. コピー先をプロジェクトルートとして確定し、Gitリポジトリでなければ `git init` を実行する。
2. 人にリモートリポジトリのURLを提示してもらう。Codexがリモートリポジトリを勝手に作成しない。
3. 接続先のURLを人に示して確認を得てから、`origin` として登録する。
4. `git remote -v` とリモートへの接続確認を行い、結果を開発ログへ記録する。
5. 生成済みの要件、計画、設定一式を日本語で初回コミットし、プッシュする。
6. URLが未提示、未確認、接続できない、または初回プッシュできない場合は、アプリ本体の実装を開始せず、状況を人へ伝える。

## 2. 作業開始前の基準点保存

変更や新機能追加の前に、次を行う。

1. `git status` で未コミットの変更を確認する。
2. 直前の正常な状態について、テストまたは動作確認を行う。
3. その作業で作成された未保存の変更があれば、内容を確認して日本語のメッセージでコミットする。
4. 人や別作業による未整理の変更は、無断でコミット、破棄、退避しない。必要なら人へ確認する。
5. 現在のブランチをリモートへプッシュし、成功を確認してから新しい作業へ進む。

コミットする変更がない場合も、現在の基準点がリモートへ反映済みであることを確認する。

## 3. 影響の大きさの判断

次のいずれかに当てはまる作業は、原則として「影響の大きい作業」とする。

- 複数の画面、機能、または主要ファイルにまたがる変更
- データベース構造、認証、権限、決済、外部API、公開設定の変更
- データ消失、情報漏えい、サービス停止につながる可能性がある変更
- 既存利用者の操作方法や保存データの互換性を変える変更
- おおむね半日を超える、または複数タスクに分かれる新機能

判断が難しい場合はIssueとブランチを使う安全側の運用とし、その理由を開発ログに残す。

## 4. Issueとブランチ

影響の大きい作業では、実装前に次を行う。

1. 背景、目的、対象範囲、対象外、完了条件、確認方法を日本語で記載したIssueを作成する。
2. Issue番号を含む作業ブランチを作成する。例: `feature/123-inventory-list`
3. Issueとブランチの対応を開発ログへ記録する。

## 5. Pull Request

作業完了後、次を日本語で記載したPRを作成する。

- 関連Issue
- 変更内容
- 変更理由
- テスト・動作確認の手順と結果
- 影響範囲と既知の制約
- レビューで特に確認してほしい点

PR作成後は人のレビュー待ちとする。Codexは明示的な依頼がない限り、PRのマージ、自動マージ設定、レビュー承認の代行を行わない。修正依頼を受けた場合は、修正、再テスト、プッシュ、PRへの日本語での報告まで行う。

## 6. 日本語で記録する範囲

次は原則として日本語で記述する。

- ソースコード内の説明コメント
- コミットメッセージ
- Issueのタイトルと本文
- PRのタイトルと本文
- レビューコメントと返信
- 開発ログ

コード、コマンド、識別子、固有名詞、一般的に英語表記するブランチ名はそのままでよい。

## 7. 開発ログと継続改善

各作業の開始時と終了時に `logs/DEVELOPMENT_LOG.md` を更新する。成功した内容だけでなく、失敗、原因、手戻り、採用しなかった案も記録する。

統括エージェントは次のタイミングでログを確認する。

- 新しいGoalまたは影響の大きい作業を始める前
- レビュー結果を統合するとき
- 同種のエラーや手戻りが発生したとき
- Goalの完了を判断するとき

再発防止策が特定できた場合は、`plans/MASTER_PLAN.md`、`tasks/TASKS.md`、`docs/DEVELOPMENT_WORKFLOW.md`、関連スキルのうち必要なものだけを更新し、更新理由をログへ記録する。
